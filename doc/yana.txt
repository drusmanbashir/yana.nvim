1. Introduction                                                      *yana*

Yana connects an installed agent CLI to Neovim. In inline mode, the agent's
proposed edits arrive as hunks for review before application. Agentic mode
writes directly; see |yana-security|.

Two public entries reach the same pipeline:

- the conversation panel, opened with |:Yana|;
- an inline edit over a line or visual selection, opened with |:YanaEdit|.

==============================================================================
2. Install                                                   *yana-install*

QUICK INSTALLATION WITH LAZY.NVIM ~

Choose the backend for the agent CLI you already use: "claude" for Claude Code,
"codex" for Codex, or "cursor" for cursor-agent. An empty opts table selects
Cursor; Yana does not automatically choose another installed agent.

Add this plugin specification to your lazy.nvim configuration: >lua

    return {
        "drusmanbashir/yana.nvim",
        dependencies = { "drusmanbashir/yana-ui.nvim" },
        opts = { backends = { default = "claude" } }, -- or "codex" / "cursor"
    }
<
lazy.nvim installs yana-ui.nvim through the dependency entry. On Ubuntu the
extra sandbox packages are bubblewrap and libcap2-bin (bwrap and capsh): >sh

    sudo apt-get install bubblewrap libcap2-bin
<
Restart Neovim in your project directory, run `:checkhealth yana`, then `:Yana`.
If bwrap:userns fails, read its host-permission diagnostic; having the packages
installed does not mean the host permits the sandbox. See |yana-health|.
Inline turns can edit your home folder and every writable data disk, wherever
the turn starts; no folder setting is needed. No model or project-path setting
is required for normal first use.

Manual start packages: >sh

    data=$(nvim --headless -i NONE -u NONE -c 'lua io.write(vim.fn.stdpath("data"))' -c qa)
    test -n "$data" || { echo "Neovim did not report its data directory" >&2; exit 1; }
    start="$data/site/pack/yana/start"
    mkdir -p "$start"
    git clone https://github.com/drusmanbashir/yana.nvim "$start/yana.nvim"
    git clone https://github.com/drusmanbashir/yana-ui.nvim "$start/yana-ui.nvim"
<

Then configure your chosen backend in Neovim: >lua

    require("yana").setup({ backends = { default = "claude" } })
<

Requirements: Linux, Neovim 0.11.2+, one agent CLI signed in: `cursor-agent`,
or, EXPERIMENTAL, `claude` or `codex`. There is no installer script: install
each system package and agent CLI yourself with the one-liners in
|yana-requirements|, which also gives the other two agent CLIs' install lines;
|yana-health| runs the same check post-install.

`apt` on Ubuntu 24.04 and older installs a Neovim below the 0.11.2+ floor
(0.9.5 on a stock Ubuntu 24.04 image, verified) with no warning of its own.
On Debian/Ubuntu, Neovim's own install docs
(https://neovim.io/doc/install/) document two ways to get 0.11.2+: the
AppImage from the Releases page, or the `neovim-ppa/unstable` PPA (not
maintained by the Neovim team): >sh

    sudo add-apt-repository ppa:neovim-ppa/unstable
    sudo apt-get update
    sudo apt-get install neovim
<

3. Requirements                                         *yana-requirements*

Required:

- Linux with user namespaces, overlayfs, and /proc
- Neovim 0.11.2 or newer (see |yana-install| for the Debian/Ubuntu
  AppImage / neovim-ppa/unstable install path and the apt-floor warning)
- one agent CLI, installed and signed in:
  - `cursor-agent` — install: >sh
        curl https://cursor.com/install -fsS | bash
<   What you need: a Cursor account (`cursor-agent login`, or
    $CURSOR_API_KEY).
  - `claude` (Claude Code CLI) — EXPERIMENTAL. Install (Anthropic's own docs,
    code.claude.com/docs/en/setup): >sh
        curl -fsSL https://claude.ai/install.sh | bash
<   What you need: an Anthropic Pro/Max/Team/Enterprise/Console account
    (run `claude` and sign in via the browser prompt, or $ANTHROPIC_API_KEY).
  - `codex` (OpenAI Codex CLI) — EXPERIMENTAL. Install
    (npmjs.com/package/@openai/codex): >sh
        npm install -g @openai/codex
<   What you need: an OpenAI ChatGPT account (`codex login`, or
    $OPENAI_API_KEY).
- bash, bwrap, capsh (from libcap2-bin/libcap-utils, used to drop
  capabilities before the confined agent starts), python3, GNU
  coreutils/findutils, util-linux mount tools, awk, sed, grep, hostname,
  getent, and id

Most required tools are checked by name only, so a non-GNU build with the
same name (e.g. BusyBox) can still pass; stat, find, date, bash, and bwrap
are checked functionally instead (GNU stat/find/date behavior, bash 4.3+
nameref support, and a real unprivileged-user-namespace probe), since those
are the ones confinement actually depends on beyond presence. The
Linux/overlayfs/proc requirement above is enforced only for confined modes
(ask, inline); direct agentic mode skips it entirely, since it never
sandboxes. Confined-mode workspace approval also requires the filesystem to
report inode birth time (stat %w); `:checkhealth yana` probes your current
working directory for this before you would otherwise hit a refusal.

Optional session discovery uses md5sum or md5. Reading titles of sessions
started outside Neovim uses sqlite3; without it, external Cursor session
titles are unavailable (those sessions still list, shown as untitled).

Run |:checkhealth| with `:checkhealth yana` after installation.

PLATFORM WARNINGS ~

- macOS is not tested on real hardware; the Darwin refusal path is covered
  only by an automated test, not a real Mac.
- WSL2 is untested. Yana has not been run against a WSL2 kernel. Ubuntu under
  WSL2 ships the same AppArmor user-namespace restriction as Ubuntu 24.04
  desktop, so expect the `bwrap:userns` remedy from `:checkhealth yana`;
  whether overlayfs behaves under WSL2's kernel has not been measured. Reports
  welcome.
- Only x86_64 is tested. Testing installs the x86_64 Neovim tarball. aarch64
  Linux is expected to work (nothing in Yana is architecture-specific) but
  has not been run.
- Fedora/RHEL is tested in a container with SELinux labelling disabled. With
  SELinux enforcing on a desktop, bubblewrap may need the `container_use_devices`
  or an equivalent boolean; if `:checkhealth yana` reports `bwrap:userns`
  failing with a permission error and the sysctl remedy does not apply, check
  `ausearch -m avc -ts recent` first.
- musl-based Linux (Alpine) is an open, named gap: Yana cannot print a cleaner
  refusal because Neovim itself fails to start before any plugin code runs.

4. Commands                                                 *yana-commands*

                                                    *:Yana*
:Yana               Toggle the panel.

                                                    *:YanaOpen* *:YanaClose*
:YanaOpen           Open the panel.
                                                    *:YanaLogin*
:YanaLogin          Sign in to the selected agent through its official login
                    in a Neovim terminal. Leave terminal input with <C-\><C-n>,
                    then q to close or cancel. Submit your prompt again after
                    login; no turn is replayed. The vendor owns credentials.
:YanaClose          Close the panel without accepting or rejecting changes.

                                                    *:YanaAsk*
:[range]YanaAsk [question]
                    Ask about the current line or supplied visual range.

                                                    *:YanaEdit*
:[range]YanaEdit [instruction]
                    Request an inline edit of the current line or range.

                                                    *:YanaRefusals*
:YanaRefusals       List system-refused artifact operations, durable metadata
                    listings, and unsafe-turn recovery paths.

                                                    *:YanaIgnore*
:YanaIgnore         List the review ignore list and the per-machine file it is
                    stored in.
:YanaIgnore {pat}   Add one gitignore-syntax pattern to that file, effective
                    immediately. A matching create/modify of a regular file is
                    written through to the workspace at turn end and never
                    offered for review; the turn reports the count and paths in
                    one line. Merged with `review.ignore` from setup(). Never
                    reaches .git/, .hg/ or .svn/, and never applies a delete,
                    symlink retarget or mode change unreviewed.

                                                    *:YanaReview*
:YanaReview         Open a pending inline review.

                                                    *:YanaAccept* *:YanaReject*
:YanaAccept         Accept the pending file change.
:YanaReject         Reject the pending file change.

                                                    *:YanaNew* *:YanaNewPanel*
:YanaNew            Start a new conversation in the current panel.
:YanaNewPanel       Open an additional panel with its own conversation.

                                                    *:YanaSessions*
:YanaSessions[!]    Attach a session owned by the live yana daemon; ! uses a
                    new panel. Sessions are resumable only while the daemon
                    that owns them is alive — nothing resumes from disk once
                    it dies.

                                                    *:YanaRecover*
:YanaRecover [id]   Recover a daemon-kept review after editor death; no id
                    reopens the recovery picker.

                                                    *:YanaMode*
:YanaMode           Switch Ask, Edit, and enabled Agent modes while the
                    conversation is quiescent: no
                    running turn and no pending or open review.

                                                    *:YanaModel*
:YanaModel          Select a model offered by the current agent.

                                                    *:YanaQueue*
:YanaQueue          Manage queued follow-up prompts.

                                                    *:YanaSteer*
:YanaSteer          Interrupt the in-flight response and resend the prompt
                    buffer as a new turn.

                                                    *:YanaAbortReview*
:YanaAbortReview    Abort the open review: put the file back as it was before
                    the hunks appeared.

                                                    *:YanaStop*
:YanaStop           Stop the active turn.

5. Configuration                                       *yana-configuration*

Use one `backends` table to choose the starting agent and set optional command
or model values. This sample also shows the common mode, inline-edit and log
settings: >lua

    require("yana").setup({
      backends = {
        default = "claude",
      },
      modes = { "inline", "ask" },
      inline_edit = { width = 37, max_height = 4 },
      log_level = "warn",
    })
<

Public setup paths~

- `backends`: table selecting and configuring installed agents.
- `backends.default`: starting agent; `cursor`, `claude`, or `codex`.
  Omission starts with Cursor.
- `backends.<name>`: optional settings for one of those agents.
- `backends.<name>.cmd`: custom executable path.
- `backends.<name>.model`: model ID for that agent.
- `modes`: available modes and their order; the first is the starting mode.
- `inline_edit`: inline-edit float settings.
- `inline_edit.enable`: enable the instruction float; default true.
- `inline_edit.width`: at most 1 means a fraction of editor columns; above 1
  means a column count. Default 0.5; minimum width 20 columns.
- `inline_edit.max_height`: maximum float rows; default 6.
- `inline_edit.history`: retained instructions; default 20. Zero disables
  history navigation.
- `log_level`: error, warn, info or debug; default info. Records below the
  selected severity are not written.

See |yana-machine-config| for custom executable paths and |yana-security| for
the workspace boundary. Key bindings and commands are listed in |yana-commands|.

6. Machine-specific configuration                       *yana-machine-config*

Yana searches Neovim's `$PATH` for the selected agent command. If Neovim cannot
find it, set a custom executable in that agent's `backends` entry: >lua

    backends = {
      default = "claude",
      claude = { cmd = "/custom/path/claude" },
    },
<

The entry may also set `model`. Run `:checkhealth yana` to check whether the
selected command is available.

7. Security                                                   *yana-security*

In `ask` and `inline`, the agent process runs in a private overlay. The agent
cannot write the real workspace; only Yana's journaled applier can do so after
an explicit acceptance. A failure to establish the overlay refuses the turn.
There is no automatic fallback to direct writes.

Non-interactive inline turns may require cursor-agent's permission-bypass flag
so its tools can run without a terminal prompt. This flag weakens the vendor's
own prompt layer. It does not weaken Yana's host boundary: Bubblewrap, the
overlay, change classification, review, and the journaled applier remain in
force. `:checkhealth yana` warns whenever this exposure applies.

Generated trees such as target, build, and __pycache__ are terminal
system-refused groups. Their bytes remain inspectable only until settlement;
their complete per-operation metadata survives for the newest five turns and
at most seven days. |:YanaRefusals| expands that metadata. Unsafe destructive
operations apply nothing, release the workspace claim, and name a preserved
recovery directory.

                                                          *yana-workspace*
WHERE A TURN MAY RUN. The workspace is the nearest `.git` root above the file
you are editing, else the file's folder; with no file open, the current
folder. It may be any folder, your home folder itself included; only `/` is
refused, before the agent starts. `:Yana --workspace DIR` binds the
next turn to a named directory. The workspace does not limit what the turn can
edit (|yana-write-scope|).

                                                        *yana-single-file*
CURRENT-FILE SCOPE. Home-dotfile and loose-file turns stay on their real paths
and use the ordinary review/accept path. `:Yana --workspace DIR` binds one
turn to `DIR`.

                                                        *yana-write-scope*
Inline writes are captured in a private overlay for review before
application, wherever they land: your home folder, every writable data disk (a
mounted ordinary filesystem whose top folder you can write) and the turn's own
folder. A home folder or disk with another filesystem mounted inside it is not
captured. Other paths, including system folders, stay read-only, and Yana
names the boundary that refused a write.

                                                        *yana-workspace-roots*
By default, the workspace is the nearest `.git` root above the file, or the
file's folder when no repository is present. `:Yana --workspace DIR` binds
one turn to a directory.

Direct `agentic` mode does not use the overlay or review. The selected agent
CLI can write directly wherever its own permissions allow. Agentic is in the
default `modes` and reached with `:YanaMode`. Omit it from the list to make it
unavailable, or list it first to start in Agent mode.

Nothing the agent prints can enable direct mode.

8. Health                                                       *yana-health*

Use: >vim

    :checkhealth yana
<

Health reports the Neovim version, resolved cursor-agent path (and, since
|yana-machine-config|, exactly which resolution step found it and every
candidate tried), required Linux tools, optional session helpers, whether
the configured skill directories and the cursor-agent chats directory were
found or skipped, current safety mode, and durable-log status. It also
probes whether the current workspace's filesystem supports the
inode birth time confined-mode approval requires. It checks yana's own
default panel keymaps against anything already mapped: a genuine collision
with a global user/plugin mapping warns, naming both sides; merely shadowing
a Neovim built-in (yana's panel keymaps are buffer-local, so e.g. `<C-s>`
submits inside the yana prompt and leaves signature-help's default
insert-mode `<C-s>` untouched everywhere else) is reported as INFO instead.
The default steer key (`<C-CR>`) is indistinguishable from plain `<CR>` on
many terminals without the Kitty keyboard protocol or an equivalent, which
health reports as INFO on a terminal it cannot confirm supports it.
Yana ships no completion provider of its own, so `<C-Space>` only shows
yana-scoped slash-command/@mention
completions when your own blink.cmp config special-cases
`vim.b.yana_prompt`, which health also reports as INFO.
Turn startup uses the same required-dependency table and refuses before the
agent starts when a required dependency is missing.

9. Events                                                       *yana-events*

                                                    *YanaReviewSettled*
`doautocmd User YanaReviewSettled` fires exactly when a review-state
transition has fully applied — paint, extmarks and the decision register all
consistent for the buffer named in its `data`. Covers: hunk accept/reject,
file accept/reject, undo/redo of a decision, review open, review close/
abort, and reload. >lua

    vim.api.nvim_create_autocmd("User", {
      pattern = "YanaReviewSettled",
      callback = function(args)
        -- args.data = { buf = <bufnr>, turn = <turn id>, reason = <string> }
      end,
    })
<
`reason` names which transition settled; the complete set is `"open"`,
`"accept_hunk"`, `"reject_hunk"`, `"accept_file"`, `"reject_file"`,
`"abort"`, `"undo_decision"`, `"native_undo"`, `"redo_decision"`,
`"native_redo"` and `"reload"`. Intended for tests and
integrations that need to know a decision has taken effect, not a fixed
delay guessed once and then either too short or too long.
