1. Introduction                                                      *yana*

Yana runs cursor-agent in a private Linux overlay and presents proposed edits
as inline hunks. The real project tree remains unchanged until the user accepts
a hunk, file, or turn.

Two public entries reach the same pipeline:

- the conversation panel, opened with |:Yana|;
- an inline edit over a line or visual selection, opened with |:YanaEdit|.

==============================================================================
2. Install                                                   *yana-install*

QUICK INSTALLATION WITH LAZY.NVIM ~

Put this complete plugin specification in
`~/.config/nvim/lua/plugins/yana.lua`: >lua

    return {
      "drusmanbashir/yana.nvim",
      dependencies = { "drusmanbashir/yana-ui" },
      cmd = { "Yana", "YanaAsk", "YanaEdit", "YanaOpen" },
      opts = {
        backend = "cursor",  -- "cursor", "claude", or "codex"
        mappings = {
          toggle = "<leader>cc",
          ask = "<leader>ca",
          inline_edit = "<C-k>",
        },
      },
    }
<
Manually: >sh

    git clone https://github.com/drusmanbashir/yana.nvim ~/.local/share/nvim/yana.nvim
<
>lua
    vim.opt.runtimepath:prepend("~/.local/share/nvim/yana.nvim")
    require("yana").setup({})
<

Requirements: Linux, Neovim 0.11.2+, one agent CLI signed in: `cursor-agent`,
or, EXPERIMENTAL, `claude` or `codex`. There is no installer script: install
each system package and agent CLI yourself with the one-liners in
|yana-requirements|, which also gives the other two agent CLIs' install lines;
|yana-health| runs the same check post-install.

`apt` on Ubuntu 24.04 and older installs a Neovim below the 0.11.2+ floor
(0.9.5 on a stock Ubuntu 24.04 image, verified) with no warning of its own.
On Debian/Ubuntu, Neovim's own install docs
(https://neovim.io/doc/install/) document two ways to get 0.11.2+: the
AppImage from the Releases page, or the `neovim-ppa/unstable` PPA (not
maintained by the Neovim team): >sh

    sudo add-apt-repository ppa:neovim-ppa/unstable
    sudo apt-get update
    sudo apt-get install neovim
<

3. Requirements                                         *yana-requirements*

Required:

- Linux with user namespaces, overlayfs, and /proc
- Neovim 0.11.2 or newer (see |yana-install| for the Debian/Ubuntu
  AppImage / neovim-ppa/unstable install path and the apt-floor warning)
- one agent CLI, installed and signed in:
  - `cursor-agent` — install: >sh
        curl https://cursor.com/install -fsS | bash
<   What you need: a Cursor account (`cursor-agent login`, or
    $CURSOR_API_KEY).
  - `claude` (Claude Code CLI) — EXPERIMENTAL. Install (Anthropic's own docs,
    code.claude.com/docs/en/setup): >sh
        curl -fsSL https://claude.ai/install.sh | bash
<   What you need: an Anthropic Pro/Max/Team/Enterprise/Console account
    (run `claude` and sign in via the browser prompt, or $ANTHROPIC_API_KEY).
  - `codex` (OpenAI Codex CLI) — EXPERIMENTAL. Install
    (npmjs.com/package/@openai/codex): >sh
        npm install -g @openai/codex
<   What you need: an OpenAI ChatGPT account (`codex login`, or
    $OPENAI_API_KEY).
- bash, bwrap, capsh (from libcap2-bin/libcap-utils, used to drop
  capabilities before the confined agent starts), python3, GNU
  coreutils/findutils, util-linux mount tools, awk, sed, grep, hostname,
  getent, and id

Most required tools are checked by name only, so a non-GNU build with the
same name (e.g. BusyBox) can still pass; stat, find, date, bash, and bwrap
are checked functionally instead (GNU stat/find/date behavior, bash 4.3+
nameref support, and a real unprivileged-user-namespace probe), since those
are the ones confinement actually depends on beyond presence. The
Linux/overlayfs/proc requirement above is enforced only for confined modes
(ask, inline); direct agentic mode skips it entirely, since it never
sandboxes. Confined-mode workspace approval also requires the filesystem to
report inode birth time (stat %w); `:checkhealth yana` probes your current
working directory for this before you would otherwise hit a refusal.

Optional session discovery uses md5sum or md5. Reading titles of sessions
started outside Neovim uses sqlite3; without it, external Cursor session
titles are unavailable (those sessions still list, shown as untitled).

Run |:checkhealth| with `:checkhealth yana` after installation.

PLATFORM WARNINGS ~

- macOS is not tested on real hardware; the Darwin refusal path is covered
  only by an automated test, not a real Mac.
- WSL2 is untested. Yana has not been run against a WSL2 kernel. Ubuntu under
  WSL2 ships the same AppArmor user-namespace restriction as Ubuntu 24.04
  desktop, so expect the `bwrap:userns` remedy from `:checkhealth yana`;
  whether overlayfs behaves under WSL2's kernel has not been measured. Reports
  welcome.
- Only x86_64 is tested. Testing installs the x86_64 Neovim tarball. aarch64
  Linux is expected to work (nothing in Yana is architecture-specific) but
  has not been run.
- Fedora/RHEL is tested in a container with SELinux labelling disabled. With
  SELinux enforcing on a desktop, bubblewrap may need the `container_use_devices`
  or an equivalent boolean; if `:checkhealth yana` reports `bwrap:userns`
  failing with a permission error and the sysctl remedy does not apply, check
  `ausearch -m avc -ts recent` first.
- musl-based Linux (Alpine) is an open, named gap: Yana cannot print a cleaner
  refusal because Neovim itself fails to start before any plugin code runs.

5. Configuration                                       *yana-configuration*

Minimal setup: >lua

    require("yana").setup({})
<

The default mode is `inline`, the first entry of `modes`. Important options: >lua

    require("yana").setup({
      -- cmd / cmd_env: see |yana-machine-config|.
      model = nil,
      modes = { "inline", "agentic", "ask" }, -- first starts; <M-t> cycles in order
      approve_mcps = false,
      -- Extra artifact-grouping names/globs; never a destructive-safety rule.
      artifact_dir_prefixes = {},
      -- Directories outside the opened workspace a turn may write.
      write_roots = {},
      mappings = { toggle = false, ask = false, inline_edit = false },
    })
<

Review keys (accept/reject a hunk, a file, or the whole turn) live in the flat
`mappings` table (default `reject_hunk="cr"`, `accept_hunk="ca"`,
`accept_file="cf"`, `accept_all="cA"`, `reject_file="cx"`, `next_hunk="]x"`,
`prev_hunk="[x"`). They cannot be disabled: `false` and `""` both restore the default. The
old `diff_keymaps` names (`ours`, `theirs`, `all_theirs`, `all_changes`,
`next`, `prev`) and the deprecated `both` alias still translate onto these;
`both` warns once per session.

The panel displays configuration mode `ask` as "Ask", `inline` as "Inline", and
`agentic` as "Agent". Its conversation winbar leads with Yana and the mode;
the prompt winbar says "Send follow-up...". Progress rows use Thinking,
Explored, Edited, and Ran. Review actions use Accept and Reject.

Direct mode is described separately because it changes the safety boundary.

Diagnostic environment variables are disabled by default:

- `YANA_DEBUG_EVENTS=1` records the raw agent stream plus a redacted decoded
  `events.jsonl` sidecar in the turn's private state directory.
- `YANA_LIFECYCLE_LOG=1` writes structured turn/claim/review lifecycle rows to
  Yana's durable log.

Both modes write extra diagnostic state. Do not enable them when a clean
default run with no diagnostic writes is required.

6. Machine-specific configuration                       *yana-machine-config*

Yana bakes in no usernames or absolute paths. Machine-specific executable
locations are resolved fresh each time they are needed.

THE AGENT BINARY ~

No environment setup is normally needed. Yana finds the built-in
`cursor-agent`, `claude`, and `codex` command names through Neovim's `$PATH`.
For a custom installation outside `$PATH`, set the matching optional variable:
`YANA_CURSOR_BIN`, `YANA_CLAUDE_BIN`, or `YANA_CODEX_BIN`. Only variables that
exist and are non-empty are used.

`cursor-agent` is resolved by `require("yana.config").resolve_cmd()`, the
single place this precedence is decided (every internal consumer asks it;
none reads `config.options.cmd` directly to spawn or probe):

  1. `cmd`, if set — an explicit path or name always wins outright.
  2. `YANA_CURSOR_BIN`, when it exists and is non-empty.
  3. The environment variable NAMED by `cmd_env` (default
     `"YANA_AGENT_BIN"`), read lazily at resolve time: you name a variable
     your shell already exports, and
     yana reads it lazily — nothing secret or machine-specific is ever a
     default.
  4. `cursor-agent` resolved on `$PATH`.

`~` is expanded (like |expand()|) on whichever candidate wins. Example: >lua

    require("yana").setup({
      -- Leave unset to use $YANA_AGENT_BIN (if exported) or PATH. Set only
      -- if cursor-agent isn't on PATH and you don't want an env var:
      -- cmd = "~/.local/bin/cursor-agent",

      -- Point this at an env var YOUR shell already exports, if it isn't
      -- YANA_AGENT_BIN. For example, if your shell profile already has
      -- `export CURSOR_CLI_BIN=/path/to/cursor-agent`:
      -- cmd_env = "CURSOR_CLI_BIN",
    })
<

`:checkhealth yana` reports exactly which step resolved (or
that none did) along with every candidate it tried, so a fresh machine says
*why* `cursor-agent` wasn't found, not just that it wasn't. See
|yana-health|.

OTHER MACHINE-SPECIFIC PATHS ~

`sessions.dir` and `sessions.chats_dir` (nil => `stdpath("data") .. "/yana"`
and `~/.cursor/chats` respectively) and `skill_dirs` (nil =>
`~/.cursor/skills`, `~/.cursor/skills-cursor`, `~/.claude/skills`) follow the
same rule: every default is a well-known relative location, expanded at the
point of use rather than hardcoded, and always overridable. A missing
optional directory degrades silently (an empty session/skill list, not an
error) and is named — found vs. skipped — by `:checkhealth yana`.

Model selection (`model`) defaults to `nil`/auto: yana never guesses or
bakes in a model name.

7. Security                                                   *yana-security*

In `ask` and `inline`, the agent process runs in a private overlay. The agent
cannot write the real workspace; only Yana's journaled applier can do so after
an explicit acceptance. A failure to establish the overlay refuses the turn.
There is no automatic fallback to direct writes.

Non-interactive inline turns may require cursor-agent's permission-bypass flag
so its tools can run without a terminal prompt. This flag weakens the vendor's
own prompt layer. It does not weaken Yana's host boundary: Bubblewrap, the
overlay, change classification, review, and the journaled applier remain in
force. `:checkhealth yana` warns whenever this exposure applies.

Generated trees such as target, build, and __pycache__ are terminal
system-refused groups. Their bytes remain inspectable only until settlement;
their complete per-operation metadata survives for the newest five turns and
at most seven days. |:YanaRefusals| expands that metadata. Unsafe destructive
operations apply nothing, release the workspace claim, and name a preserved
recovery directory.

                                                          *yana-workspace*
WHERE A TURN MAY RUN. The workspace is the nearest `.git` root above the file
you are editing, else a configured `workspace_roots` entry, else the folder
itself. It may be any folder, not only a git project — but never your whole
home directory, `/`, or a top-level folder such as `/home` or `/tmp`. Those
are refused by name before the agent starts, with the remedy "pick a project
subdirectory". Depth is counted in path components below `/` after resolving
symlinks: `/` is 0, `/home` is 1 (refused), `/home/you` is your home (refused
by the home rule, via `$HOME` and via your passwd entry), `/home/you/notes` is
3 (allowed). The rule exists because a top-level folder is never a project:
accepting it would put every sibling under the agent's write scope. Start
Yana inside the project or folder you mean to change. When the file you mean
to edit would otherwise be refused or is loose, huge, or explicitly pinned,
Yana may run in |yana-single-file| instead.

                                                        *yana-single-file*
SINGLE-FILE MODE. When a turn would otherwise use a refused or oversized
workspace, Yana runs the agent against a scratch copy of exactly ONE file.
The review paints in your real buffer; the agent's confined writes land only
in the scratch workspace; your `:w` writes the real file. Reads stay the
jail's read-only view of the host. A file inside a git project below `$HOME`
is never single-file, whatever its folder size.

WHEN IT TRIGGERS. Checks run in this order; the first match wins:

1. `single_file.enabled = false` — single-file mode is off; ordinary workspace
   rules apply.
2. `:Yana --workspace DIR` on this turn — widens the workspace; single-file
   mode is not entered.
3. The file is behind the secrets wall — turn refused (see REFUSALS below).
4. The file is not saved to disk yet — turn refused.
5. `:Yana --file` — forced for this turn only.
6. The file's folder would be refused as a workspace (`/`, `$HOME`, passwd
   home, or depth < 2 below `/` after resolving symlinks) — trigger `home`.
7. The file has no `.git` ancestor below `$HOME` — trigger `loose`.
8. The file's folder has more than `single_file.max_entries` entries (default
   2000; non-recursive `readdir`) — trigger `huge`.
9. Otherwise — ordinary folder mode (not single-file).

WHAT THE AGENT MAY TOUCH. Exactly one file: a byte-equal copy in the scratch
workspace. Multi-file edits, create, delete, and chmod are refused by name.
Declared `write_roots` are unavailable in single-file mode.

SCRATCH COPY. Yana creates under the state root (`$XDG_STATE_HOME/nvim` by
default, overridable with `YANA_STATE_ROOT`):

    <state_root>/single-file/<sha16>/ws/<basename>
    <state_root>/single-file/<sha16>/records/     " scratch turn records
    <state_root>/single-file/<sha16>/meta.json    " real_path, real_workspace

`<sha16>` is the first 16 hex digits of a hash of the file's real path. The
`ws/` tree is wiped and recopied at each single-file turn; it is removed when
the turn ends or the review closes. Yana never writes a `.yana` directory
under `$HOME` for these turns.

BANNER. While a single-file turn is open, the prompt winbar shows:

    Single-file mode · agent edits only <basename> · multi-file/create/delete refused · :Yana --workspace DIR to widen

REFUSALS (verbatim; `<basename>` and `<rel>` are filled in by Yana):

                                                              *yana-sfm-refusals*
`single-file mode: <basename> is behind the secrets wall`
    Open a file outside the masked secrets paths.

`single-file mode: save <basename> first`
    `:write` the file to disk, then start the turn.

`single-file mode: could not read <basename>`
    Fix permissions or disk errors and retry.

`single-file mode: declared write roots are not available`
    Remove `write_roots` or use `:Yana --workspace DIR` to widen.

`single-file mode: only <basename> may change (refused <rel>)`
    The agent proposed another file or a non-modify change; the allowed file's
    hunk may still be offered.

`single-file mode: the buffer is closed — reopen <basename> and decide again`
    `:edit` the file, then accept or reject again.

`single-file mode: buffer differs from the composed review — decide again`
    Reconcile the real buffer with what you want, then decide again.

ACCEPT, REJECT, UNDO. Accept (`ca`) lands the hunk in the real buffer and
marks it `modified`; the real disk file is unchanged until your `:w`. Reject
(`cr`) restores the pre-turn lines in the real buffer. Once the review closes
it stays closed: `u` in the real buffer is plain Neovim undo — bytes may move,
no review reopens. The review lives in the real buffer, not the scratch copy.

DISABLE OR FORCE. >lua

    require("yana").setup({
      single_file = {
        enabled = false,
        max_entries = 2000,
      },
    })
<
`:Yana --file` forces single-file mode on the next panel turn only.
`:Yana --workspace DIR` widens the workspace for one turn and skips
single-file mode.

                                                        *yana-write-roots*
`write_roots` declares directories OUTSIDE the opened workspace that a turn may
write. The opened workspace is always the first root and is never listed. Each
declared root is confined, claimed, walked, reviewed and applied exactly like
the workspace: its edits arrive as ordinary hunks (the panel names the root
when a turn has more than one), and its real files change only after you accept
them. A write into any directory that is neither the workspace nor declared
here still fails read-only, and the refusal now names the exact line that would
allow it. Entries are absolute (a leading `~` is expanded); a root that does
not exist, that overlaps the workspace or another root, or that lives inside
yana's own state directory refuses the turn by name before the agent starts.
Nothing the agent says can add or widen a root. Each declared root costs one
more overlay mount and one more claim per turn (measured about 180ms). >lua

    require("yana").setup({
      write_roots = { "~/code/fran", "~/code/det3d" },
    })
<

                                                        *yana-capture-root*
`capture_root` is the ONE directory a turn's single overlay is mounted at. Every
write beneath it — the opened repository, a sibling repository declared nowhere,
a directory that did not exist when the turn started — lands in the turn's
private layer instead of failing read-only, and the review groups the hunks by
each file's own nearest `.git` root, computed from what the turn wrote rather
than declared before it. One mount and one claim, however many repositories the
turn touches. Unset, yana chooses it from filesystem position: `~/code` when the
resolved workspace is under it, else `$HOME`, else the workspace itself — never
a directory that contains yana's own state root. Anything outside it is still
read-only and the refusal still names the line that would allow it. The claim
stays on the opened repository, so a second turn on a different repository under
the same capture root starts freely; when two turns propose changes to the same
file, the second to ACCEPT it is refused by name, naming the holder. Nothing the
agent says can choose it. >lua

    require("yana").setup({
      capture_root = "~/code",
    })
<
                                                    *yana-workspace-roots*
`workspace_roots` names directories that are a workspace even though they hold
no `.git`. A turn's workspace is the nearest `.git` root at or above the file
you have open; failing that, the `workspace_roots` entry that contains it;
failing that, the file's own folder. A repository always wins, because the
repository is what a claim is taken on. >lua

    require("yana").setup({
      workspace_roots = { "~/notes" },
    })
<

`artifact_dir_prefixes` adds directory-component names or globs for grouping only. It
may change an individual binary proposal from durable recovery to momentary
retention. It never grants destructive safety and never changes the
authoritative change bundle.

Direct `agentic` mode does not use the overlay, review, or diary. With the
default `sandbox.agentic = "full"`, the selected agent CLI gets the same user
permissions it gets in a terminal, including paths outside the opened
workspace. Agentic is in the default `modes` and reached with `<M-t>`; leave it
out of the list to make it unreachable, or list it first to start in it: >lua

    require("yana").setup({
      modes = { "agentic", "inline", "ask" },
      sandbox = { inline = "vendor-default", agentic = "full" },
    })
<

`sandbox` selects Yana's vendor-neutral level. Valid levels are `full`,
`workspace`, `read-only`, and `vendor-default`; the last appends no vendor
sandbox flag. Ask always uses `read-only`. Each backend translates the selected
level into its own CLI spelling; a backend missing a level refuses at setup.
Inline defaults to `vendor-default`: Yana's overlay is the write boundary, so
no second vendor sandbox token is added. A system-wide vendor config may still
narrow a declared `write_roots` entry; |yana-health| warns when this inheritance
is active.

Nothing the agent prints can enable direct mode.

8. Health                                                       *yana-health*

Use: >vim

    :checkhealth yana
<

Health reports the Neovim version, resolved cursor-agent path (and, since
|yana-machine-config|, exactly which resolution step found it and every
candidate tried), required Linux tools, optional session helpers, whether
the configured skill directories and the cursor-agent chats directory were
found or skipped, current safety mode, and durable-log status. It also
probes whether the current workspace's filesystem supports the
inode birth time confined-mode approval requires. It checks yana's own
default panel keymaps against anything already mapped: a genuine collision
with a global user/plugin mapping warns, naming both sides; merely shadowing
a Neovim built-in (yana's panel keymaps are buffer-local, so e.g. `<C-s>`
submits inside the yana prompt and leaves signature-help's default
insert-mode `<C-s>` untouched everywhere else) is reported as INFO instead.
The default steer key (`<C-CR>`) is indistinguishable from plain `<CR>` on
many terminals without the Kitty keyboard protocol or an equivalent, which
health reports as INFO on a terminal it cannot confirm supports it — rebind
it, e.g. `mappings = { steer = "<M-CR>" }`, if `<C-CR>` never steers for you.
Yana ships no completion provider of its own, so `mappings.completion_menu`
(default `<C-Space>`) only shows yana-scoped slash-command/@mention
completions when your own blink.cmp config special-cases
`vim.b.yana_prompt`, which health also reports as INFO.
Turn startup uses the same required-dependency table and refuses before the
agent starts when a required dependency is missing.

9. Events                                                       *yana-events*

                                                    *YanaReviewSettled*
`doautocmd User YanaReviewSettled` fires exactly when a review-state
transition has fully applied — paint, extmarks and the decision register all
consistent for the buffer named in its `data`. Covers: hunk accept/reject,
file accept/reject, undo/redo of a decision, review open, review close/
abort, and reload. >lua

    vim.api.nvim_create_autocmd("User", {
      pattern = "YanaReviewSettled",
      callback = function(args)
        -- args.data = { buf = <bufnr>, turn = <turn id>, reason = <string> }
      end,
    })
<
`reason` names which transition settled; the complete set is `"open"`,
`"accept_hunk"`, `"reject_hunk"`, `"accept_file"`, `"reject_file"`,
`"abort"`, `"undo_decision"`, `"native_undo"`, `"redo_decision"`,
`"native_redo"` and `"reload"`. Intended for tests and
integrations that need to know a decision has taken effect, not a fixed
delay guessed once and then either too short or too long.

vim:tw=78:ts=8:noet:ft=help:norl:
